# RLVR：奖励来自可验证的结果

## 直觉

RLVR（Reinforcement Learning with/from Verifiable Rewards）按奖励来源分类：模型输出能被程序、规则、编译器、单元测试、数学答案检查器或可执行环境可靠判定时，便可给出可验证奖励。它不是 PPO、DPO 或 GRPO 的替代算法名称；例如可用 PPO 或 GRPO 最大化 RLVR 回报。它与 RLHF 的核心区别是主要监督信号不必来自人类比较或人类训练的奖励模型。

## 前置知识

对提示 `x` 生成完整解 `y`，验证器 `v(x,y)` 返回 0/1 或标量：

```
R(x,y) = v(x,y)
maximize  E_(y~πθ)[R(x,y)] - β * KL(πθ || πref)
```

这是简化式。验证器可只检查最终答案（outcome reward），也可检查代码测试、格式、工具调用状态等。即使奖励可验证，策略仍需一个优化器；GRPO 的组相对优势或 PPO 的价值/优势估计都可接在这里。

## 流程

选择任务并实现确定性验证器；先做对抗性单测，确认它不接受明显错误解；采样多个候选，运行验证器得到奖励；用选定 RL 算法更新，持续审计通过率以外的质量。验证器版本、沙箱权限、超时和随机种子都应记录，否则“可验证”无法复现。

## 小例子

要求写函数排序数组：在隔离环境运行隐藏测试，所有测试通过为 1，否则 0。模型可能写出针对公开测试的硬编码，所以隐藏测试、性质测试和资源限制属于奖励设计的一部分。数学题若只比最终数值，也可能奖励猜对而非可读推理；是否奖励过程取决于验证器能验证什么。

## 常见误区

可验证不等于完美或有价值。验证器只证明其编码的性质，可能有漏洞、覆盖不足或与用户目标不一致。RLVR 也不保证泛化到开放式写作、同理心或复杂价值判断，那些领域往往仍需要人类偏好或其他监督。不要将“规则奖励”与“无 reference”混为一谈：实际 RLVR 常仍以 SFT 模型为参考并加 KL。
