## 前置：把一次前向变成一段前缀

自回归目标模型每产生一个 token 都依赖前缀；即使用 KV cache，用户可见延迟仍受这些串行轮次支配。投机解码让便宜的草稿器先顺序提出 $\gamma$ 个 token，随后让目标模型沿这条已知路径一次计算所有位置的 logits。验证通过的连续前缀可以立刻提交。因此它省的是目标模型的串行调用数，绝不意味着输出不再由目标模型的分布决定。

记已生成上下文为 $s$，草稿为 $y_{1:\gamma}$。第 $i$ 个位置的目标和草稿条件分布分别是 $p_i(x)=p(x\mid s,y_{<i})$、$q_i(x)=q(x\mid s,y_{<i})$。两者须用同一词表，且 $q_i(x)>0$ 的 token 必须可由 $p_i$ 定义。它们的温度、top-p 或 top-k 变换可以不同；关键是式中的 $q_i$ 必须等于草稿**实际抽样**后的分布，$p_i$ 必须等于产品要保留的目标抽样分布。

## 原理推导：接受与正残差

抽到 $y_i$ 后，以

$$
a_i(y_i)=\min\left(1,{p_i(y_i)\over q_i(y_i)}\right)
$$

接受它。第一处拒绝时，从残差 $r_i$ 抽一个替代 token：

$$
r_i(x)={ [p_i(x)-q_i(x)]_+ \over \sum_v[p_i(v)-q_i(v)]_+ }.
$$

若 $\gamma$ 个均通过，额外从 $p_{\gamma+1}$ 抽一个 token。这个额外 token 让每轮至少前进一格，也使下一轮拥有正确的上下文。

无偏性可在单位置直接看出。token $x$ 经“草稿后接受”输出的质量为 $q(x)\min(1,p(x)/q(x))=\min(p(x),q(x))$；拒绝事件的总质量为 $Z=\sum_v[p(v)-q(v)]_+$，而残差抽到 $x$ 的质量为 $Zr(x)=[p(x)-q(x)]_+$。二者相加恰为 $p(x)$。条件在每一个已接受前缀上都成立，递归后完整序列仍服从目标分布。这里的“无损”是分布意义；浮点、截断词表或错误地拿 logits 当 $q$ 都会破坏前提。

## 具体算例

令词表为 A、B、C，$p=(0.30,0.50,0.20)$，$q=(0.40,0.20,0.40)$。草稿提出 A 时接受率是 $0.30/0.40=0.75$；提出 B 时必然接受。拒绝质量是 $0.10+0.20=0.30$，残差只在 B 上有 $0.30$，故修正 token 为 B。A 的最终质量为 $0.40\times0.75=0.30$；B 的质量为 $0.20+0.30=0.50$；C 同理为 $0.20$。它不是“拒绝后从 $p$ 重抽”：那样会把已接受的质量再算一次。

## 可运行代码：统计检验而非性能测试

文件 [speculative-decoding.py](../../examples/inference/speculative-decoding.py) 固定上述分布，做十万次独立实验。它不加载模型，也不报告吞吐；输出频率接近 $p$ 才是这个玩具程序要验证的性质。

```python
from random import Random

TOKENS, P, Q = ("A", "B", "C"), (0.30, 0.50, 0.20), (0.40, 0.20, 0.40)
def draw(w, rng):
    u = rng.random(); total = 0.0
    for token, value in zip(TOKENS, w):
        total += value
        if u < total: return token
    return TOKENS[-1]
def step(rng):
    y = draw(Q, rng); i = TOKENS.index(y)
    if rng.random() < min(1.0, P[i] / Q[i]): return y
    residual = [max(p-q, 0.0) for p, q in zip(P, Q)]
    return draw([v/sum(residual) for v in residual], rng)
```

完整文件还会累计接受率和观测频率。实现多 token 版本时，验证 logits 的形状通常是 `[batch, gamma+1, vocab]`：第 $i$ 行对应携带草稿前缀的 $p_i$，不能把同一行复制给所有候选位置。

## 工程权衡

期望每轮提交长度随着接受率与 $\gamma$ 增长，但草稿器本身也耗时，目标验证要为候选分配 KV cache 和批量槽位。低接受率、很短的回复、草稿器太重、或高并发时的验证浪费都可能消去收益。greedy 的“相同就接受”能复现 greedy 路径，却不是上面的采样算法；生产系统还应一致处理 EOS、过滤器和 logit processor，记录实际接受长度、目标/草稿时间与端到端延迟，再做参数选择。

### 一轮运行的状态机

实现时可把一轮拆成五个不可混淆的状态。第一，草稿器从当前已提交前缀顺序抽 $\gamma$ 次，并保存每次的 token、log probability、随机数或可重放种子。第二，目标模型把这些 token 作为连续输入，以正确的位置编码和 KV cache 计算 $\gamma+1$ 处的分布。第三，从首个 token 开始比较 $p_i/q_i$，一旦拒绝立刻停止检查后继。第四，在拒绝处从残差抽一个 token；第五，把已接受前缀和修正 token 写入序列及 cache。全接受分支则写入 $\gamma$ 个草稿和一个目标补 token。把“提案、验证、提交”写成同一个循环常会产生 off-by-one：例如拿 $p_i$ 验证 $y_{i+1}$，或把补 token 当作下一轮草稿的第一项。

采样处理器应在何处执行也很关键。若对目标做 repetition penalty、禁词或温度缩放，$p$ 必须是处理后的分布；草稿侧的 $q$ 也应记录自己实际经过的处理。目标单独采用 top-p 并不构成错误，仍可与草稿的实际 $q$ 比较；真正的错误是草稿也经过截断或重归一化抽样，却拿截断前的概率当 $q$。EOS 可以被接受并立即终止；不要在 EOS 后继续填草稿 token。多请求批处理还必须按每条请求自己的拒绝位置截断，不能让同批其他序列的长度影响其随机性。

### 何时值得采用

草稿与目标越接近、请求越长、目标单步延迟越高，投机往往越有空间；但这些是方向而非保证。设目标单步耗时为 $T_p$、草稿单步为 $T_q$、一次验证额外开销为 $T_v$，应观察每轮平均提交长度而不是只看接受率。一个草稿器即使单 token 接受率高，若 $\gamma$ 很短或 $T_q$ 接近 $T_p$，端到端仍未必受益。反之，较低的尾部接受率可能仍值得，因为已接受前缀减少了用户等待的目标轮次。正确的实验需要同一模型权重、同一采样参数、相同请求集和冷暖 cache 条件，并给出 p50、p95、tokens/s 与显存。

### 边界与诊断

“目标分布不变”不等于每一个带固定随机种子的实现会逐 token 与非投机生成相同；两种算法消耗随机数的顺序不同。可比的是大量样本的分布、或在精心对齐 RNG 后的测试轨迹。诊断偏差时，先在很小词表枚举 $p,q$，验证每个 token 的质量之和；再检查残差质量是否等于拒绝概率。诊断慢时，按轮记录草稿时间、目标验证时间、已提案数、已接受数、拒绝位置和 cache 内存。只有这样才能判断该缩短草稿、换轻草稿器，还是优化验证 kernel。

还应区分模型调用次数与实际硬件时间。目标验证虽将多个候选放进一次前向，但该前向的序列长度更长，attention、logits 采样和 cache 写入并非零成本；不同 GPU、量化格式和 batch size 会改变它们的比例。草稿器可以是独立小模型、目标模型的早退层或专门预测器，只有“能快速提出且其概率定义清楚”才适合精确采样。离线指标最好同时给出平均草稿长度和平均验证长度，以免高提案数伪装成高效率。

一个最低限度的回归套件应包括：$p=q$ 时所有草稿必接受；$p$ 与 $q$ 支持差异很大时残差仍归一；固定 EOS 的路径不会多提交 token；批处理重排后单请求的统计分布不变。它们测试的是算法不变量，而不是某张显卡的速度。

这些检查也使后续替换草稿器时能保持同一正确性基线。

## 自测

1. 为什么拒绝后不能直接从 $p$ 重抽？

<details>
<summary>答案</summary>

接受步骤已给 token 分配 $\min(p(x),q(x))$ 质量；残差恰补足差额。

</details>

2. $p(y)<q(y)$ 时接受率是什么？

<details>
<summary>答案</summary>

$p(y)/q(y)$，并非零。

</details>

3. $\gamma$ 个草稿全通过后为何补目标 token？

<details>
<summary>答案</summary>

它保证进度，并取得草稿块之后正确的目标条件分布。

</details>
