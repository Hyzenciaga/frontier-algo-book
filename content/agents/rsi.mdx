# Recursive Self-Improvement（RSI）：把改进过程也置于可验证闭环中

递归自我改进不是“模型在回答后说一句反思”，也不是一个已经统一的训练算法。它描述的是一个系统把改善自身能力、研发流程或能力生产率作为任务；被验收的改进进入下一轮，下一轮因而能够提出或验证更好的候选。被改的对象可以是代理代码、搜索策略、训练配方、数据管线、提示词、工具链或参数。严肃讨论 RSI 的起点是把循环拆开：改什么、谁生成候选、谁执行、谁评估、通过什么门槛以及失败如何回滚。

## 前置知识

设系统版本为 $A_t$，候选改动为 $c_t$，评估器给出向量指标 $m(c_t)$。只有在资源预算 $B$、安全约束 $C$ 和独立保留评测 $H$ 下，接受函数 $g$ 认可候选，才有 $A_{t+1}=apply(A_t,c_t)$。递归来自 $A_{t+1}$ 参与产生或筛选下一轮候选，并不要求一次循环改神经网络。这里必须区分三个层：更新记忆或提示词会改变调用上下文；提交代码改变运行系统；重新训练才改变模型参数。三者都可能改善能力，却有不同成本和证据要求。

## 机制

一个可审计的 RSI 系统至少含五个隔离部件。提案器根据失败日志、代码和历史试验提出可复现 patch 或配置；执行器在受限沙箱中构建并运行；测量器收集正确性、成本、延迟和安全结果；独立验收器只读取冻结的保留任务；版本控制器记录工件哈希、环境、随机种子、指标与回滚点。循环可概括为

$$
c_t\leftarrow propose(A_t,D_t),\quad m_t\leftarrow evaluate(c_t;H,B,C),\quad A_{t+1}=\begin{cases}apply(A_t,c_t)&g(m_t)=1\\A_t&g(m_t)=0\end{cases}
$$

“独立”并不一定指完全不同的模型，但验收数据、评分器、调参访问权限和候选生成路径不能共享会让答案泄漏的通道。若提案器能看到保留题、反复查询同一 benchmark 的逐题反馈，或把测试输出写回训练记忆，最终分数不再估计未知任务表现。更隐蔽的泄漏来自依赖缓存、环境状态、手工挑选的失败案例和多轮选择后只报告最佳试验。解决它需要冻结测试、记录尝试次数、预先指定门槛，并定期换新评测而非只加大样本量。

RSI 的关键评估不是“新版本是否更强”，而是“**改进过程是否更会改进**”。除了能力曲线，应测每单位预算产生的有效候选数、从失败到可验证 patch 的周期、在新任务上接受率、回归率、人工干预率与安全拒绝率。若 $A_{t+1}$ 只在同一个熟悉基准更高分，但提案质量、保留任务收益和边际收益不提高，它可能只是普通调参或过拟合，而非可持续的过程改善。收益也不必指数增长：验证吞吐、算力、数据新颖性、搜索空间和错误累积都可使曲线趋平。

普通自训练与 RSI 有交集但不等价。自训练常指模型产生伪标签或轨迹，再训练自身；它可以成为一个候选生成器或数据模块。要构成 RSI，还需外部可验证的选择、版本化接受和下一轮从已接受改进受益的因果链。相反，一个自动优化编译配置、从不更新模型权重的系统，只要闭环确实提升其后续搜索与验收能力，也可属于受限的流程级 RSI。不要把这种局部自动化外推为无界的“智能爆炸”。

## 例子

本例以训练分数和冻结保留分数区分候选，只有保留集相对当前基线至少提高 5 分才部署；可运行文件见 [完整 Python 示例](../../examples/agents/rsi.py)。

```python
"""Toy acceptance gate: accept progress, reject regressions and small gains."""
candidates = [("cache-v1", 88, 86), ("overfit-fast", 98, 72),
              ("cache-v2", 93, 89), ("planner-v3", 96, 92)]
baseline = 80
accepted = []
for name, train_score, holdout_score in candidates:
    improves = holdout_score >= baseline + 5
    print(f"{name:11} train={train_score} holdout={holdout_score} accept={improves}")
    if improves:
        baseline = holdout_score
        accepted.append(name)
print("accepted:", accepted, "baseline:", baseline)
assert accepted == ["cache-v1", "planner-v3"] and baseline == 92
```

结果中 `cache-v1` 被接受，基线由 80 提高到 86；`overfit-fast` 的训练分数虽高，保留分数下降，因此拒绝；`cache-v2` 只提高 3 分，未过门槛；`planner-v3` 提高 6 分，被接受后基线成为 92。这里演示的是**相对于已接受版本继续改进**，而非所有候选都与最初的 80 分比较。

真实系统远比此例复杂：指标应包含置信区间、回归套件、成本与安全约束；候选必须在隔离环境运行；保留集也会被长期使用而耗尽。代码中的门槛是教学设定，拒绝的候选从未应用，因此不需要真正执行回滚。它并未生成候选、训练模型或证明任何版本更聪明。

## 深入：循环速度不是递归能力

把更多代理并行起来会增加候选数，却可能只放大同一种偏见。真正的过程改进应在相同预算下带来更高质量的假设、更快的反例发现或更可靠的验收。可用消融实验检验：冻结提案器而只升级执行器、冻结评测器而只升级检索、移除历史试验记录，比较各模块对保留任务与下一轮候选质量的因果贡献。若没有这种对照，“后一版更高”也可能只是多花了计算。

评估器本身也是会被优化的对象，故需要评估的评估：交叉实验室或独立脚本复跑、隐藏测试轮换、对抗性候选和回放旧版本。候选若能修改验收逻辑，更应把验收器置于不可写边界；否则系统最短路径可能是让测试更容易通过。RSI 的实务价值正在于把这种元层面的失效模式变成可观测、可拒绝的工程事件。

资源账本也属于闭环。每个候选应消耗可计量的 GPU 时间、工具额度、人工复核和失败预算；接受一个微小收益但大幅增加维护负担的版本，可能降低系统长期的实验速度。把成本放入门槛，才可比较“更强”与“更会改进”。在任何涉及真实用户或生产权限的场景，候选测试与部署授权必须分层：可在沙箱里自动拒绝的改动，不应因一次离线高分获得外部写入能力。

## 常见误区

自动反思、写入 memory 或一轮 prompt 优化都只是可能的部件。没有独立验收与跨轮版本因果，就不能据此声称递归改进。仅看训练曲线也不能证实能力增加，因为循环本身会把选择压力施加到已见任务。另一误区是把人类设定目标、选择指标和批准部署视为“失败”：在人类在环的受限系统里，这些控制正是可审计性来源。研究问题在于哪些环节可自动化且仍可验证，而不是删除所有门槛。

3. 一个仅更新检索规则的系统，何时可算流程级 RSI？
