# DSpark：半自回归草稿与置信度调度

## 前置：并行草稿的末端为何容易失效

DSpark（Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation）处理两件相连的事。纯并行块草稿可以很快给出长候选，却因块内缺少 token 间依赖而在越后的位置越容易与目标分歧；固定地验证整块又会让高拒绝风险的后缀占用 batch 容量。DSpark 以半自回归草稿改善前者，以置信度和负载感知的前缀调度改善后者。

它仍是投机解码器：被送入验证的 token 必须由目标概率最终接受或拒绝，随机采样仍需要 $p/q$ 接受率和正残差。置信度是预测“值得花一次验证容量吗”的调度信号，不能当作 token 正确性的裁决，更不能替代目标 logits。

## 原理：顺序补偿与前缀调度

对块长 $B$，并行 backbone 一次产生位置表征 $H\in\mathbb{R}^{B\times d}$。DSpark 额外加入轻量顺序模块：第 $j$ 个位置接收前一草稿 token 或其 embedding 的状态，使 $\tilde h_j=G(h_j,\tilde h_{j-1},y_{j-1})$。这不是把完整大草稿又改回串行 Transformer；序列模块的目标是在很小的延迟预算里恢复关键的块内条件依赖，从而减轻 suffix decay。

confidence head 给出每位置的**条件**接受概率 $c_j=P(\text{第 }j\text{ 位通过}\mid1{:}j-1\text{ 均通过})$。对真实条件概率，链式法则精确给出前 $k$ 位的存活概率 $S_k=\prod_{j=1}^k c_j$；head 输出是这些概率的预测值，乘积也只是存活概率的估计。论文以该累计量估计预期接受长度，并用 Sequential Temperature Scaling 从左到右校准它。调度器结合引擎吞吐曲线和当前负载：低负载时多验证一些候选的边际成本小；高负载时低 $S_k$ 后缀会挤掉其他请求，最优 $k$ 会变短。它只可截去后缀，不能跳过第 2 位却验证第 3 位，因为投机提交必须是连续前缀。

## 具体算例

设五个位置的置信度是 $(0.94,0.86,0.72,0.43,0.21)$。前两位存活估计为 $0.808$，前四位降至约 $0.250$，第五位仅约 $0.053$。空闲 GPU 可能仍验证四位以争取更长提交；高负载下，若额外验证一位的吞吐收益低于其 batch 成本，调度器应在较短前缀停止。无论选择两位还是四位，目标在真实验证中仍可能在第一位拒绝；这些数字不是接受保证。

## 可运行代码

[dspark.py](../../examples/inference/dspark.py) 用相同的五个置信度和两个 load 值枚举一个显式教学效用函数，输出各自的验证长度。函数及系数均为人造，故输出只能说明调度会随负载改变，不能表示 DSpark 实测吞吐。

```python
"""Toy prefix scheduler: expected progress per artificial latency, not a DSpark benchmark."""
CONFIDENCE = (.94, .86, .72, .43, .21)

def choose_prefix(load):
    survival, progress = 1.0, 1.0  # includes correction or bonus token
    best_len, best_rate = 0, 1.0
    for length, c in enumerate(CONFIDENCE, 1):
        survival *= c
        progress += survival
        latency = 1 + .1 * length + load * .12 * length ** 2
        rate = progress / latency
        if rate > best_rate:
            best_len, best_rate = length, rate
    return best_len

for load in (.2, 1.0):
    print("load:", load, "prefix:", choose_prefix(load))
assert choose_prefix(.2) == 3 and choose_prefix(1.0) == 2
```

代码的 `progress = 1 + sum(S_j)` 来自尾和公式，包含首拒绝时的修正 token，或全通过后的 bonus token。不能仅用 `k * S_k`：那会把“没有整块全过，但仍提交了较短前缀”的收益全部漏掉。这里用人造二次延迟项表示负载下的边际成本，输出低负载前缀 3、高负载前缀 2；真实调度需要替换为引擎测量曲线。

## 工程权衡

置信度必须校准；若换目标版本、领域、temperature、thinking 模式或 tokenizer，离线置信度可能失真，草稿器也常需再训练。调度器需要真实的 engine profile：不同 batch、上下文长度、KV cache 压力和 SLA 下，“多验一位”的成本不同。比较时应分开报告离线接受长度、单请求 latency、固定吞吐和生产负载曲线。论文所述相对 MTP-1 的线上速度区间属于 DeepSeek-V4 服务条件，不能外推成任意电脑的承诺。

### 为什么是半自回归

若每个位置只读取同一份上下文特征和自己的位置编码，模型只能猜测“第六个位置通常长什么样”，却不能利用本轮第五个草稿 token 已经选择了什么。完全自回归草稿能解决该问题，但又恢复 $B$ 次顺序调用。DSpark 的结构在两端之间取折中：大部分表征并行完成，轻量序列部件沿块内传播必要状态。其价值不在于声称无依赖，而在于把最昂贵的深层网络从每个位置的串行路径中移开。

顺序部件自身的误差也会累积，所以不能只把它看作“免费的 RNN”。训练与评测需按真实草稿 token 运行，检查改善是否集中在后缀接受率；若它只提高第一位，说明并行 backbone 或目标特征接口仍是瓶颈。比较纯并行、全自回归和半自回归时，应固定块长、候选预算、目标模型与采样设置，否则获得的速度差可能只是验证工作量不同。

### 置信度的校准与策略

$c_j$ 可理解为条件在前缀存活时第 $j$ 位被接受的估计，而非语言模型对该 token 的原始概率。好模型不仅排序正确，也要数值校准：被预测为约 0.8 的桶，实际接受比例应接近 0.8。可按领域、位置和负载分桶画 reliability diagram；若末端总是过度自信，调度器会反复把无效后缀交给目标，吞吐反而下降。策略也可加入请求的剩余长度、deadline 与 batch 中其他请求，而不是只设一个全局阈值。

一个安全的实现边界是：调度器只决定“验证从第 1 位连续取到第 k 位”，验证器再独立执行接受和修正。这样改变 profile 或负载只改变成本和延迟，不改变某个已验证位置的概率规则。若让置信度直接接受 token，模型校准误差会成为输出分布偏差；若允许跳跃验证，则后面 token 的条件前缀本身不再成立。

### 线上观察指标

除了平均 accepted length，还应监控每个负载桶的被验证数、拒绝位置直方图、置信度校准误差、队列等待、KV cache 占用与用户可见 token 间隔。若吞吐提升但 p99 恶化，可能是过长验证块对少数请求造成 head-of-line blocking；若低负载单请求变慢，则调度器的 profile 把并发收益错当成局部收益。上线最好从记录模式开始：先用置信度给出建议长度而不改变执行，校验预测与实测后再逐步启用。

调度的粒度还会影响公平性。若系统总把容量给预计高接受率的请求，短而困难的请求可能长期等待；实际服务可给每个请求设置最小验证进度，再用置信度分配余量。profile 也不应永久固定：模型量化、GPU 驱动、请求长度分布或连续批处理策略改变后，原先的最优前缀可能失效。将 profile 版本、草稿 checkpoint 版本和线上采样参数一起记录，才有能力解释一次吞吐回归。

离线表格中的平均值还应附带分位数或按任务类别拆分。某配置也许在短聊天中只多验一个 token，却在长代码补全中显著改善后缀；只汇总成单个 accepted length 会掩盖这种差异，也难以指导真实服务路由。

因此，配置选择应随工作负载演进，而非一次调参后永久冻结。

## 自测

1. 顺序模块补什么？

<details>
<summary>答案</summary>

纯并行块中相邻草稿 token 的条件依赖。

</details>

2. 置信度能代替目标验证吗？

<details>
<summary>答案</summary>

不能；它只调度验证预算，正确性仍由目标概率与残差给出。

</details>

3. 负载为何改变前缀？

<details>
<summary>答案</summary>

相同后缀在高负载占用更稀缺的 batch 容量，边际吞吐成本不同。

</details>
