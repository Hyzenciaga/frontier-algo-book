# DFlash：用块扩散草稿并行猜 token

## 直觉

普通草稿模型也要一个 token 接一个 token 地写，草稿阶段仍是串行的。DFlash（Block Diffusion for Flash Speculative Decoding）把草稿限定为一个轻量的块扩散模型：它在一次前向中提出一个 token 块，再交给自回归目标模型验证。把扩散模型放在「提案者」位置，目标模型仍保持最终裁决，因而不必把扩散模型当成独立回答模型来承受其质量差距。

## 前置

它是投机解码的草稿器替换，而非新的采样正确性规则。部署端仍应以标准 `p/q` 接受和残差重采样保证随机采样与目标分布一致；若系统只做 greedy，则是在验证目标的贪心选择。DFlash 需要针对特定目标模型训练，并读取目标模型抽取的上下文特征，因此不是任意两个现成模型随手配对就能得到论文效果。

## 机制

论文的核心是「目标最懂自己的未来」：自回归目标的隐藏特征带有多 token 的未来信息。DFlash 从目标模型抽取上下文特征，作为轻量块扩散草稿器的条件；草稿器并行生成块内多个候选 token。随后目标模型对整块做验证，接受连续前缀并在拒绝处按标准投机采样修正。草稿块的并行性降低草稿时间，但块内 token 不按左到右依赖也带来问题：越靠后的 token 往往越容易被拒绝。

## 例子

设目标需要回答代码补全，DFlash 一次提议 7 个 token。目标验证后前 5 个连续通过，第 6 个被拒绝：运行时提交前 5 个，在第 6 位从残差分布采样一个 token，然后开始下一轮。即使一次提议了 7 个，也没有「整块全中才有收益」：接受前缀已经节省了多次目标模型串行调用。

## 误区

「单次前向出一块」不等于所有 token 同样可靠；长块会使尾部接受率下降。论文报告的超过 6 倍 lossless acceleration 是特定模型、任务与服务设置的实验结果，不能视为所有硬件、上下文长度或并发下的承诺。也不要把 DFlash 的扩散草稿与最终输出的采样机制混为一谈：无损性来自验证器的接受/残差校正。

## 自测

1. DFlash 的扩散并行性主要省掉目标模型还是草稿模型的串行工作？
2. 块末尾拒绝率上升时，增加块长一定更快吗？
3. 为什么 DFlash 仍必须让目标模型验证？
