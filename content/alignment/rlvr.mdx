# RLVR：奖励来自可验证的结果

## 直觉

当答案能由编译器、单元测试、符号求解器或精确匹配检查时，训练信号不必近似人的偏好。RLVR（reinforcement learning with verifiable rewards）把验证器输出作为奖励；它降低了奖励模型的主观误差，却把正确性定义交给验证器规格。

## 前置知识与机制推导

设验证器 $v(x,y)\in\{0,1\}$，目标是 $J(\theta)=\mathbb E_{y\sim\pi_\theta}[v(x,y)]$；可加入长度/格式项和 $-\beta KL$。二元末端奖励稀疏：一条正确轨迹中每个 token 获同一正回报，错误轨迹全负或零，因此 credit assignment 粗糙。若单样本成功率 $p$，独立采样的 pass@k 为 $1-(1-p)^k$；训练提高 $p$ 与推理增加 $k$ 是不同资源交换。

## 数据流程

定义输入生成器、隔离执行环境、时间/内存限制和不可伪造的 oracle；生成候选、运行验证、保存输出与失败类型，再用 PPO/GRPO 等更新。测试必须藏在训练外，题目按家族切分；否则模型可能记住答案。对代码应防止读取测试、网络与非确定性；对数学须规范化等价表达，避免把格式错当推理错。

## 正确结果不等于正确过程

结果 verifier 可以接受 `42`，却看不到模型是否由错误代数、猜测或泄露答案得到它。对需要可靠过程的任务，应增加步骤检查、可执行证明、过程奖励模型或抽样人工审计；但步骤 verifier 自身也会引入可投机表面模式。RLVR 只保证相对于 $v$ 的最优，不保证隐含推理真实、可迁移或符合未编码约束。

解析器是攻击面。若判题器将输出转整数，`"42 junk"`、NaN、溢出、Unicode 空白或多答案分隔符可能和作者预期不同；若用 shell 拼接候选代码，输出甚至可能逃逸沙箱。验证器应有严格语法、规范化后唯一表示、属性测试、资源限额和失败即拒绝的默认策略。示例里 `strip()` 接受前后空白是有意规格，不能不经说明推广为“宽松就安全”。

数据泄露同样会把奖励曲线伪装成推理进步：训练题、公开题解、hidden test 或同一题的变量替换若跨集合出现，模型可记忆字符串。应以题目家族、生成模板、时间和来源切分；保留未公开的评测生成器，并检查 n-gram/语义近邻重合。一个可手算链路：候选通过则 $r=1$、失败为 $0$；同题组内回报 $(1,0,0,1)$ 产生正负相对优势，PPO/GRPO 才会提高两条通过轨迹的 token 概率。若 verifier 被 `print(42)` 绕过，则训练会高效学会绕过，而非学会任务。

## 小例子

```python
"""结果验证器的二元奖励与 pass@k。"""
import math
p, k = .18, 8
print("pass@%d=" % k, round(1-(1-p)**k, 4))
for answer in ["42", " 42 ", "forty two"]:
    print(repr(answer), int(answer.strip() == "42"))
```

运行 `python examples/alignment/rlvr.py` 的 pass@8 约为 `0.7956`；第二行通过是因为 verifier 明确做了空白规范化。 [下载示例](../../examples/alignment/rlvr.py)

## 常见误区

“可验证”不等于“任务目标完整”：单元测试覆盖不全仍可被过拟合。零奖励不表示回答毫无价值，可能只是 oracle 太窄。把推理过程写得像正确答案也不会替代真正执行验证。

## verifier 给出的证据边界

通过测试证明的是“该输入、该资源限制和该实现下接受”，不是程序对所有输入正确。随机测试会漏掉低概率反例；数学等式的浮点容差会接受近似但不等价的解；代码沙箱若允许读环境变量，隐藏答案可能成为输入。应保存 verifier 版本、seed、运行镜像、stderr 和超时原因，使奖励可追溯；独立的 hidden generator 与对抗测试才能把证据范围扩展到训练分布之外。
